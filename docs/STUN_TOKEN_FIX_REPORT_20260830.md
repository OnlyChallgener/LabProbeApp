# STUN 稳定性与 Token 图表修复报告（2026-08-30）

## 1. 结论

本轮 STUN 状态反复跳动的主因在 LabRelay 的 TCP STUN 探测与恢复逻辑，不是 Hub/App 同步链路重复下发规则。

- 第二条 WireGuard 使用 UDP STUN，因此最稳定。
- 第一、第三、第四条均为 TCP STUN；真机出现的“读取响应失败/连接失败”会被旧逻辑一次性降级为 `mapping`，Hub 每 3–5 秒同步后，App 立即从“地址已获取”跳成“正在校验”。
- Hub 状态同步只转发 Relay 的运行快照。规则内容一致时不会重复执行 upsert，也没有证据表明同步链路在反复重启规则。
- 默认 TCP STUN 服务已做协议级复现：单连接以 5 秒、20 秒间隔连续 Binding 均成功，三条并发 TCP 连接也全部成功。因此不存在“服务端固定只允许一条 TCP 连接”的限制。
- 真机问题符合运营商/NAT 路径偶发关闭空闲 TCP，以及固定本地端口断线后旧连接进入 TIME_WAIT、短期阻碍同四元组重连的组合现象。

## 2. Relay 修复

LabRelay 版本从 `0.2.30` 提升到 `0.2.31`，确保更新器不会把新二进制误判为已安装版本。

1. TCP STUN Binding 保活从 20 秒缩短为 10 秒，降低上级 NAT/运营商链路回收空闲连接的概率。
2. TCP STUN 会话失败后使用 abortive close（RST）释放旧连接，再重新建立连接，避免固定本地端口长期卡在 TIME_WAIT。
3. 首 12 次恢复尝试每 5 秒一次，随后每 15 秒持续探测；不再在短暂失败后很快退到 30 秒慢轮询。
4. 最近 90 秒内成功确认过的映射遇到一次或数次临时失败时继续保持 `mapped`，App 不再闪黄。
5. 连续 90 秒没有任何成功 Binding 才降级为 `mapping`；旧公网地址保留为历史，但不作为新确认地址。
6. 任意一次 Binding 成功都会更新确认时间、恢复 `mapped` 并清除错误。
7. 错误改为保留完整原因链，后续若仍有真机异常，可以看到连接失败背后的具体系统错误，而不只是一句顶层文案。

该处理符合 RFC 8489 对 TCP STUN 失败连接“重新打开 TCP 连接”的要求，并保留了真实长期故障的可见性。
